# QA Handoff — Issue #15: Verification Plugin Framework

## Summary

The verify stage was refactored from monolithic inline logic to a generic plugin dispatch model. LLM judge logic was extracted into `harness/lib/plugins/judge.sh` (invoked as a subprocess), and a latent bug was fixed where the old code read from an undefined `$judge_result_file` variable, causing every judge invocation to fail silently and pass.

## Test Steps

**Setup**: All steps below assume you have a working harness install under `harness/` with `yq` and `jq` available. Run from the repo root.

### 1. Confirm `config_load` preflight rejects an unknown plugin key

Create a throwaway config that references a non-existent plugin:

```bash
cat > /tmp/qa-bad-plugin.yaml <<'EOF'
backend: claude
stages:
  - name: test-stage
    prompt: prompts/triage.md
    verify:
      notareal:
        foo: bar
EOF
bash harness/run.sh --config /tmp/qa-bad-plugin.yaml --item 1
```

Expected: `config_load` fails immediately with an error message that names the unknown plugin key (`notareal`) and the directories it checked. The harness exits before any LLM call.

### 2. Confirm `config_load` accepts a config whose verify keys all resolve

Run `config_load` against the default config — which has `judge` in the `review` stage's verify block:

```bash
bash -c '
  source harness/lib/config.sh
  config_load harness/config/default.yaml && echo "config_load OK"
'
```

Expected: prints `config_load OK` with no errors. This proves `judge.sh` is found under `harness/lib/plugins/`.

### 3. Invoke `judge.sh` directly and confirm it emits valid JSON

Construct a minimal stage record directory and call the plugin as a subprocess:

```bash
stage_dir="$(mktemp -d)"
run_dir="$(mktemp -d)"
printf '{"prompt":"prompts/judge-review.md","schema":"schemas/judge.json"}' > "$stage_dir/judge"
printf 'claude' > "$stage_dir/backend"
bash harness/lib/plugins/judge.sh "$stage_dir" "$run_dir" 1 "Co-Authored-By: Test"
```

Expected: stdout is a single line of JSON with exactly the keys `passed`, `verdict`, and `reason`. If the backend is unavailable, `passed` is `false` and `reason` is a specific error string (e.g. `"judge invocation failed"`). The script must not exit non-zero — `_judge_fail` always exits 0 with a well-formed JSON object.

### 4. Confirm the plugin dispatch path in `verify_stage`

Run `verify_stage` directly with a `verify` block that references the `judge` plugin:

```bash
stage_dir="$(mktemp -d)"
run_dir="$(mktemp -d)"
printf '{}' > "$run_dir/facts.json"
printf '{"judge":{"prompt":"prompts/judge-review.md","schema":"schemas/judge.json"}}' > "$stage_dir/verify"
printf 'claude' > "$stage_dir/backend"

bash -c '
  source harness/lib/verify.sh
  verify_stage "'"$stage_dir"'" "'"$run_dir"'" 1 "Co-Authored-By: Test"
'
```

Expected: stdout is a JSON object with `passed` (bool), `checks` (empty array `[]`), `plugins` (object with a `judge` key), `warnings`, and `failure_reason`. The `plugins.judge` object contains `passed`, `verdict`, and `reason`. There are no top-level `judge_verdict` or `judge_reason` fields.

### 5. Confirm the old silent-pass bug is fixed

Call `judge.sh` with an empty judge config so the plugin fails explicitly:

```bash
stage_dir="$(mktemp -d)"
run_dir="$(mktemp -d)"
printf 'null' > "$stage_dir/judge"
printf 'claude' > "$stage_dir/backend"
result="$(bash harness/lib/plugins/judge.sh "$stage_dir" "$run_dir" 1 "Co-Authored-By: Test")"
echo "$result" | jq '.passed'
```

Expected: prints `false`. Under the old code this would have exited without emitting JSON at all (reading from an undefined `$judge_result_file`), which `verify_stage` would then have interpreted as a silent pass. The fix ensures a broken judge always produces `{"passed": false, ...}`.

### 6. Confirm `executor.sh` writes the full `verify:` block to `stage_record_dir/verify`

Run the full harness against the default config with an issue that reaches the `review` stage, then inspect the run directory:

```bash
bash harness/run.sh --config harness/config/default.yaml --item <issue-number>
# After the run completes or aborts:
cat .harness/runs/<run-id>/telemetry.jsonl | jq '.verify.plugins'
```

Expected: the telemetry entry for the `review` stage shows a `verify.plugins.judge` object (not top-level `judge_verdict`/`judge_reason`). The `verify` object in telemetry is whatever `verify_stage` emitted.

## Expected Behavior

- `config_load` fails fast and names the offending key when a verify block references a plugin with no matching `lib/plugins/<key>.sh`.
- `verify_stage` dispatches each non-`checks` key in the `verify:` block to `lib/plugins/<key>.sh` as a subprocess.
- A plugin that exits non-zero, emits non-JSON, or emits JSON without a boolean `passed` field causes the stage to fail with reason `"plugin did not return a valid verdict"`.
- `judge.sh` always exits 0 and always emits a `{"passed":bool,"verdict":"pass"|"fail","reason":"..."}` object, even when the judge config is missing, the prompt cannot be assembled, or the backend invocation fails.
- The final verdict JSON from `verify_stage` has the shape `{passed, checks: [...], plugins: {<name>: {...}}, warnings: [], failure_reason}`. There are no top-level `judge_verdict` or `judge_reason` fields.

## Edge Cases

| Scenario | Expected outcome |
|---|---|
| `verify:` block has a key with no matching `lib/plugins/<key>.sh` | `config_load` fails at load time with a named-key error message; the harness never starts |
| Plugin script is present but crashes (non-zero exit, empty stdout) | `verify_stage` records `{"passed":false,"verdict":"fail","reason":"plugin did not return a valid verdict"}` for that plugin; stage fails |
| Plugin exits 0 but emits non-JSON or JSON without `passed` | Same as above — `jq -r '.passed // empty'` returns empty, triggering the invalid-verdict path |
| Plugin exits 0 with `{"passed":false,...}` (plugin-reported fail) | Plugin verdict is stored verbatim; stage fails; `failure_reason` includes the plugin's `reason` string |
| `judge.sh` config missing or null | `_judge_fail "judge config is missing or null"` — emits `{"passed":false,...}`, exits 0 |
| `_CONFIG_DIR` set to a consuming repo that has its own `lib/plugins/judge.sh` | Plugin resolution prefers the config-dir override; the harness install's plugin is not used |

## Impact Notes

**Removed top-level fields**: The verdict JSON no longer contains `judge_verdict` or `judge_reason` at the top level. These fields were present in the pre-refactor `verify.sh` output. Any downstream reader of `telemetry.jsonl` or direct `verify_stage` output that accessed `.judge_verdict` or `.judge_reason` would break.

**Confirmed no internal consumers**: `executor.sh` reads only `.passed` and `.failure_reason` from the verdict (lines 254–258), and `telemetry.sh` stores the entire `verify_json` blob opaquely. Neither file references `judge_verdict` or `judge_reason`. A repo-wide search confirms the only occurrence of these names is in `harness/lib/plugins/judge.sh`, where they are local variables inside the plugin script — not field names written to the verdict JSON.
